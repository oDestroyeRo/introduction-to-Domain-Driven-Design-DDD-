    Speaker notes:

    Say: Today is an introduction to Domain-Driven Design. This is not a framework talk and not a clean architecture debate. The focus is how product, business, and engineering can describe the same business problem clearly.

    Set expectation: In 60 minutes we will cover the ideas you need to recognize where DDD helps: language, boundaries, context maps, and a few tactical patterns.

    Transition: Start by explaining why normal software projects become hard even when the technology stack is familiar.

    02 / 16

    Software gets hard when meaning is unclear

    Many systems are not difficult because of databases or APIs. They are difficult because the business language is inconsistent.

    A

    Different teams use the same word for different ideas.

    B

    Rules live in conversations, tickets, spreadsheets, and code comments.

    C

    The data model becomes the business model by accident.

    Speaker notes:

    Say: A lot of software complexity is not caused by databases or APIs. It comes from unclear meaning. One team says order and means cart intent; another team says order and means paid customer commitment.

    Ask: What is one business word in our work that different teams use differently? Examples: customer, order, product, shipment, payment, account.

    Transition: DDD gives us tools to make these meanings explicit before they become accidental architecture.

    03 / 16

    DDD is a design discipline for complex domains

    Domain-Driven Design helps teams build a software model that matches the business model well enough to support change.

    Discover Learn the domain with experts.
    Model Name concepts and behavior clearly.
    Bound Keep meanings consistent inside clear contexts.
    Speaker notes:

    Say: DDD is a discipline for designing software around the domain: the business problem we are trying to solve. It works best when the domain has real rules, exceptions, and language that matter.

    Explain the loop: Discover the domain with experts, model the important concepts and behavior, then bound that model so each meaning stays consistent.

    Transition: The session is based on three books. I will use their ideas, but attendees do not need to have read them first.

    04 / 16

    We use the original book, a modern practical guide, and a concise distilled overview.

    Eric Evans

    Vaughn Vernon

    Speaker notes:

    Say: These are the three references behind the session. Evans gives the original deep treatment. Khononov gives a modern practical way to choose patterns by business complexity. Vernon gives a concise overview that is easier to start with.

    Reading advice: If someone is new, start with Distilled, then Learning Domain-Driven Design, then use Evans as the deeper reference.

    Transition: With the references clear, move into the first mindset shift: domain-first instead of data-first.

    05 / 16

    Domain-first thinking changes the starting point

    DDD does not start with tables. It starts with the behavior and language of the business.

    Data-first

    • Tables first
    • Generic services
    • Rules scattered across layers
    • Names mirror storage

    Domain-first

    • Business behavior first
    • Explicit model language
    • Rules near the model
    • Names mirror the domain
    Speaker notes:

    Say: Data modeling is important, but DDD asks us not to start there. If we start with tables, we often lock in storage names before we understand the behavior.

    Example: In a marketplace, product in catalog is information for discovery. Product in ordering may be a snapshot used for price and fulfillment. If we force one table-shaped meaning too early, the model becomes confusing.

    Transition: Once we start from the domain, we need two levels of practice: strategic design and tactical design.

    06 / 16

    DDD has two layers of practice

    Strategic DDD decides the boundaries. Tactical DDD shapes the model inside a boundary.

    Strategic

    Where does the model apply?

    Domain, subdomain, bounded context, context mapping, team ownership.

    Tactical

    How does the model behave?

    Entity, value object, aggregate, repository, domain service, domain event.

    Speaker notes:

    Say: Strategic DDD answers where a model applies. Tactical DDD answers how the model behaves inside that boundary.

    Emphasize: Strategic design usually comes first. If we jump directly to entities and aggregates without boundaries, we may create complicated code that still has unclear meaning.

    Transition: To talk about boundaries, first define domain and subdomain.

    07 / 16

    A domain is the business problem space

    A subdomain is a smaller area of business capability inside that problem space.

    Marketplace
    Product catalog
    Order management
    Payment processing
    Shipping coordination
    Customer support
    Speaker notes:

    Say: A domain is the overall business problem space. A subdomain is a smaller business capability inside it.

    Marketplace example: The marketplace contains catalog, ordering, payment, shipping, and support. They are connected, but each has different rules and priorities.

    Transition: Not every subdomain deserves the same level of design investment. That is why DDD separates core, supporting, and generic domains.

    08 / 16

    Not all subdomains deserve the same investment

    DDD helps teams focus design effort where business differentiation is highest.

    Core domain

    Competitive advantage

    Invest most modeling effort here.

    Supporting domain

    Business-specific but not unique

    Build enough to fit the business.

    Generic domain

    Common capability

    Buy, reuse, or integrate when practical.

    Speaker notes:

    Say: The core domain is where the business wins or differentiates. Supporting domains are business-specific but not the main advantage. Generic domains are common capabilities that many companies need.

    Example: For a marketplace, matching supply and demand may be core. Payment gateway integration may be supporting or generic depending on the company. Authentication is often generic.

    Transition: Once we know where to invest, the next tool is language. DDD treats language as part of the model, not decoration.

    09 / 16

    Ubiquitous Language is the shared model in words

    The team agrees on the words and uses them in conversations, tickets, diagrams, APIs, tests, and code.

    Term Meaning in Ordering
    Order Customer commitment to buy selected items.
    Shipment Fulfillment movement after an order is accepted.
    Cancellation Business decision before the order is shipped.
    Speaker notes:

    Say: Ubiquitous Language means the team uses the same words in meetings, tickets, diagrams, APIs, tests, and code. The language is not only for documents; it shapes the model.

    Example: If the Ordering context says cancellation means before shipment, that meaning should appear in tests, API names, and code behavior.

    Transition: Shared language needs a boundary. Without a boundary, the same word will eventually need multiple meanings.

    10 / 16

    A Bounded Context protects meaning

    Inside a bounded context, a model and its language are consistent. Outside it, the same word may mean something else.

    Catalog context Product

    Information buyers use to discover and compare items.

    Ordering context Product

    A purchasable item snapshot used to calculate an order.

    Speaker notes:

    Say: A Bounded Context is a boundary where one model and one language are consistent. Outside the boundary, the same word can mean something else.

    Important: A bounded context is not automatically a microservice. It can be a module, a team boundary, or later a service boundary. First it is a boundary of meaning.

    Transition: After defining contexts, we can draw how they cooperate with a context map.

    11 / 16

    Example context map: marketplace order flow

    A context map shows how different models cooperate without pretending they are one universal model.

    Catalog Product discovery
    Ordering Cart, order, cancellation
    Payment Charge, refund, settlement
    Shipping Parcel, pickup, tracking
    Support Case, claim, resolution
    Speaker notes:

    Say: This context map shows a marketplace order flow. Catalog helps the customer discover a product. Ordering creates a cart and order. Payment handles charge and refund. Shipping handles parcel movement. Support handles exceptions.

    Walkthrough: Move left to right. Catalog product becomes an order line snapshot. A paid order becomes a payment fact. A shipment request becomes a parcel process. These handoffs are between related but different models.

    Transition: Now move from strategic design into tactical modeling inside a context.

    12 / 16

    Tactical models start with identity and value

    Entity and value object are small concepts, but they prevent a lot of accidental complexity.

    Entity

    • Has identity over time
    • Can change state
    • Example: Order, Customer

    Value object

    • Defined by values
    • Usually immutable
    • Example: Money, Address
    Speaker notes:

    Say: An entity has identity over time. A value object is defined by its values. This small distinction prevents many modeling mistakes.

    Ask: If two addresses have the same values, are they the same address for this model? Usually yes. If two orders have the same items and price, are they the same order? Usually no, because each order has its own identity.

    Transition: Entities and value objects are often grouped into aggregates, which protect business rules.

    13 / 16

    An aggregate is a consistency boundary

    An aggregate groups model objects that must change together to protect business rules.

    Order
    Order Line
    Shipping Address
    Payment Intent

    Rule: an order cannot be confirmed if required payment information is missing.

    Speaker notes:

    Say: An aggregate is a consistency boundary. It groups objects that must change together to protect business rules, also called invariants.

    Example: In an order aggregate, the rule might be that an order cannot be confirmed unless required payment information exists. The aggregate protects that rule before state changes are accepted.

    Transition: When something important happens in the domain, we can name it as a domain event.

    14 / 16

    Domain events name important business facts

    A domain event is something meaningful that already happened inside the domain.

    01OrderPlaced
    02PaymentAuthorized
    03ShipmentRequested
    04OrderDelivered
    Speaker notes:

    Say: A domain event is an important business fact that already happened. That is why event names are usually past tense, such as OrderPlaced or PaymentAuthorized.

    Explain: Events help teams see workflows and integration points. They do not mean every context must share the same data model; they create a clear handoff between models.

    Transition: Now give the group a small exercise to practice language, boundaries, and tactical patterns together.

    15 / 16

    Exercise: model a marketplace order

    Scenario: a customer places an order, pays for it, and waits for delivery.

    1

    List domain terms

    Order, customer, payment, parcel, refund, cancellation.

    2

    Draw bounded contexts

    Separate meanings for catalog, ordering, payment, shipping, support.

    3

    Mark model patterns

    Find entities, value objects, aggregates, and domain events.

    Speaker notes:

    Say: We will model a simple marketplace order. The goal is not to create a perfect diagram. The goal is to practice asking better domain questions.

    Facilitate: Give 4 minutes to list terms and draw boundaries, 2 minutes for discussion, and 2 minutes to summarize. Ask groups to identify at least one ambiguous word and one possible domain event.

    Transition: Close by summarizing what they should remember and where to continue reading.

    16 / 16

    Takeaways

    • Model the domain, not only the database.
    • Use shared language to reduce ambiguity.
    • Draw boundaries before choosing service boundaries.
    • Apply tactical patterns where complexity justifies them.
