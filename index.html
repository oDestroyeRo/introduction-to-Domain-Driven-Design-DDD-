    Shared language Clear boundaries Better models

    Speaker notes:

    Say: Today is an introduction to Domain-Driven Design. This is not a framework talk and not a clean architecture debate. The focus is how product, business, and engineering can describe the same business problem clearly.

    Set expectation: Use this as a guided conversation. Pause on the examples, ask whether the same ambiguity exists in your team, and connect each DDD idea back to a real workflow.

    Example: We will use a marketplace checkout: one buyer purchases items from multiple shops, pays once, and the platform splits the purchase into shop orders.

    Transition: Start by explaining why normal software projects become hard even when the technology stack is familiar.

    02 / 16

    Software gets hard when meaning is unclear

    The same word can hide different business meanings.

    Speaker notes:

    Say: A lot of software complexity is not caused by databases or APIs. It comes from unclear meaning. One team says order and means cart intent; another team says order and means paid customer commitment.

    Example: In the same marketplace, order might mean a buyer checkout order, a seller shop order, a payment record, or a shipment request. If we do not separate the meanings, the code starts mixing responsibilities.

    Ask: What is one business word in our work that different teams use differently? Examples: customer, order, product, shipment, payment, account.

    Transition: DDD gives us tools to make these meanings explicit before they become accidental architecture.

    03 / 16

    DDD is a design discipline for complex domains

    Build a model that can change with the business.

    Discover
    Model
    Bound
    Speaker notes:

    Say: DDD is a discipline for designing software around the domain: the business problem we are trying to solve. It works best when the domain has real rules, exceptions, and language that matter.

    Explain the loop: Discover the domain with experts, model the important concepts and behavior, then bound that model so each meaning stays consistent.

    Example: Instead of starting with an orders table, ask what must happen in the business: reserve price, authorize one payment, split by shop, and notify fulfillment.

    Transition: The session is based on three books. I will use their ideas, but attendees do not need to have read them first.

    05 / 16

    Domain-first thinking changes the starting point

    Start with behavior and language before storage shape.

    Speaker notes:

    Say: Data modeling is important, but DDD asks us not to start there. If we start with tables, we often lock in storage names before we understand the behavior.

    Example: In a marketplace, product in catalog is information for discovery. Product in ordering may be a snapshot used for price and fulfillment. If we force one table-shaped meaning too early, the model becomes confusing.

    Transition: Once we start from the domain, we need two levels of practice: strategic design and tactical design.

    06 / 16

    DDD has two layers of practice

    Boundaries first. Model behavior second.

    Strategic

    Boundaries

    Tactical

    Behavior

    Speaker notes:

    Say: Strategic DDD answers where a model applies. Tactical DDD answers how the model behaves inside that boundary.

    Emphasize: Strategic design usually comes first. If we jump directly to entities and aggregates without boundaries, we may create complicated code that still has unclear meaning.

    Example: Strategic design separates Checkout, Payment, Shop Orders, and Fulfillment. Tactical design then decides whether ShopOrder is an aggregate and which events it emits.

    Transition: To talk about boundaries, first define domain and subdomain.

    07 / 16

    A domain is the business problem space

    Subdomains are smaller business capabilities.

    Marketplace
    Product catalog
    Checkout
    Shop order management
    Payment processing
    Fulfillment coordination
    Customer support
    Speaker notes:

    Say: A domain is the overall business problem space. A subdomain is a smaller business capability inside it.

    Example: The marketplace contains catalog, checkout, payment, shop-order management, fulfillment, and support. They are connected, but each has different rules and priorities.

    Transition: Not every subdomain deserves the same level of design investment. That is why DDD separates core, supporting, and generic domains.

    08 / 16

    Not all subdomains deserve the same investment

    Spend design effort where the business wins.

    Core domain

    Competitive advantage

    Supporting domain

    Business-specific but not unique

    Generic domain

    Common capability

    Speaker notes:

    Say: The core domain is where the business wins or differentiates. Supporting domains are business-specific but not the main advantage. Generic domains are common capabilities that many companies need.

    Example: For a marketplace, matching supply and demand may be core. Payment gateway integration may be supporting or generic depending on the company. Authentication is often generic.

    Transition: Once we know where to invest, the next tool is language. DDD treats language as part of the model, not decoration.

    09 / 16

    Ubiquitous Language is the shared model in words

    One vocabulary across conversation, design, and code.

    Speaker notes:

    Say: Ubiquitous Language means the team uses the same words in meetings, tickets, diagrams, APIs, tests, and code. The language is not only for documents; it shapes the model.

    Example: If Checkout says buyer order, Shop Orders says shop order, and Fulfillment says shipment, those names should appear in tickets, tests, API names, and code behavior.

    Transition: Shared language needs a boundary. Without a boundary, the same word will eventually need multiple meanings.

    10 / 16

    A Bounded Context protects meaning

    One boundary. One consistent meaning.

    Catalog context Product
    Checkout context Product
    Speaker notes:

    Say: A Bounded Context is a boundary where one model and one language are consistent. Outside the boundary, the same word can mean something else.

    Important: A bounded context is not automatically a microservice. It can be a module, a team boundary, or later a service boundary. First it is a boundary of meaning.

    Example: In Catalog, product describes searchable information and shop offer details. In Checkout, product is a line snapshot with price and seller at the moment the buyer pays.

    Transition: After defining contexts, we can draw how they cooperate with a context map.

    11 / 16

    One checkout, one payment, many orders

    Checkout groups items by shop. After payment succeeds, the platform creates one confirmed order per shop.

    Catalog Product discovery Products and shop offers
    Checkout Shop-grouped checkout Draft before payment
    Payment One charge Whole checkout amount
    Orders Per-shop confirmed orders Buyer and shop see the same split
    Fulfillment Pickup, parcel, tracking Handled per shop order
    Published Language Catalog -> Checkout Offer snapshot
    Customer/Supplier Checkout -> Payment Payment request
    Published Language Payment -> Orders PaymentSucceeded
    Customer/Supplier Orders -> Fulfillment Fulfillment request
    Speaker notes:

    Say: This context map shows the marketplace rule more accurately: before payment, Checkout is not yet the final order. Checkout is a purchase attempt that groups items by shop and asks Payment to charge the buyer once.

    Walkthrough: Catalog publishes an offer snapshot to Checkout. Checkout requests one payment for the whole checkout. After payment succeeds, Orders creates one confirmed order per shop. The buyer sees the same separate orders, and each shop sees only the order it must fulfill.

    Important: Different roles are only a clue, not an automatic bounded-context split. In this marketplace, buyer-facing order history and shop-facing order work can be different views of the same per-shop order model because the confirmed order is already split by shop.

    Design note: If Payment integrates an external gateway, Payment can protect the marketplace model with an anti-corruption layer instead of leaking gateway terms into Checkout.

    Example: A buyer buys a phone case from Shop A and a charger from Shop B. Checkout contains two shop groups. Payment charges the buyer once. After success, Orders creates Order A for Shop A and Order B for Shop B. The buyer sees both orders; Shop A sees only Order A; Shop B sees only Order B.

    Transition: Now move from strategic design into tactical modeling inside a context.

    12 / 16

    Tactical models start with identity and value

    Identity is not the same as value.

    Entity

    Identity over time

    Value object

    Defined by values

    Speaker notes:

    Say: An entity has identity over time. A value object is defined by its values. This small distinction prevents many modeling mistakes.

    Example: BuyerOrder and ShopOrder are entities because each has an identity and lifecycle. Money, Address, and OrderLineSnapshot are usually value objects because their meaning comes from their values.

    Ask: If two addresses have the same values, are they the same address for this model? Usually yes. If two orders have the same items and price, are they the same order? Usually no, because each order has its own identity.

    Transition: Entities and value objects are often grouped into aggregates, which protect business rules.

    13 / 16

    An aggregate is a consistency boundary

    Protect the rules that must always be true.

    Buyer Order
    Order Line
    Shipping Address
    Payment Reference

    Invariant protected here

    Speaker notes:

    Say: An aggregate is a consistency boundary. It groups objects that must change together to protect business rules, also called invariants.

    Example: In a buyer order aggregate, the rule might be that the order cannot be confirmed unless a payment authorization reference exists. The aggregate stores the reference or status, while the Payment context still owns charge, refund, and settlement behavior.

    Transition: When something important happens in the domain, we can name it as a domain event.

    14 / 16

    Domain events name important business facts

    Name the business facts that already happened.

    01BuyerOrderPlaced
    02PaymentAuthorized
    03ShopOrderCreated
    04ShipmentDelivered
    Speaker notes:

    Say: A domain event is an important business fact that already happened. That is why event names are usually past tense, such as BuyerOrderPlaced or PaymentAuthorized.

    Explain: Events help teams see workflows and integration points. They do not mean every context must share the same data model; they create a clear handoff between models.

    Example: In the marketplace flow, useful events might be BuyerOrderPlaced, PaymentAuthorized, ShopOrderCreated, FulfillmentRequested, and ShipmentDelivered.

    Transition: Now give the group a small exercise to practice language, boundaries, and tactical patterns together.

    16 / 16

    Takeaways

    Domain Language Boundaries Patterns
    Speaker notes:

    Say: The main takeaway is that DDD helps us model the business, not only the database. Start with language, then boundaries, then tactical patterns where complexity justifies them.

    Recommended next step: Pick one real workflow, such as marketplace order placement, and map the terms, business rules, context boundaries, and important events before discussing architecture.

    Example: For the checkout workflow, write down BuyerOrder, Payment, ShopOrder, FulfillmentRequest, and Shipment. Then mark which context owns each word and which event moves work to the next context.

    Close: For reading, start with Vernon for the short overview, Khononov for practical pattern choice, and Evans for the deeper original reference.
